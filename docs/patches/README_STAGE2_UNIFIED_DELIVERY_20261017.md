# Lackey — Stage 2 / единый движок доставки (17.10.2026)

## База

Полный проект собран на основе `Lackey_stage1_20261015.zip`. Все исправления
первого этапа сохранены. Архив НЕ включает `.env`, базы данных, токены и кэш.

## Что изменилось

- `application/services/delivery.py` — один выходной путь `DeliveryPipeline`
  для текста, одиночного медиа, альбома, forward и reply. При получении от
  Telegram ID отправленных сообщений постобработка Mongo/статистики/реакций
  происходит отдельно от send, поэтому **не может вызвать повторный send**.
- `application/services/relay.py` — одна проверка политик для групповых/ЛС
  сообщений, медиа и пересылки. Действующий redirect проверяется до доставки.
  Доставка из ЛС учитывает `/anon` для всех форматов. У обычных сообщений
  можно настроить ограничения по топику `/settopic`.
- `application/services/reply.py` — reply на каждый видимый элемент составного
  сообщения (заголовок / вложение / пересланный оригинал / элемент альбома).
  Отправляет ответ в **исходный** топик, сохранённый при первой доставке, а не
  в текущий `/settopic` чата. Sticker/video_note идут как два отдельных
  сообщения, оба как reply на исходное.
- `database.py` + `adapters/mongo/repositories.py` — ОДНА запись `threads`
  на логическую доставку. Старые scalar-поля `origin_message_id` и
  `relay_message_id` сохранены. Новые поля:
  `origin_message_ids`, `relay_message_ids`, `origin_anchor_message_id`,
  `origin_topic_id`, `relay_topic_id`. Индексы по парам чат+массив ID
  создаются автоматически при старте. Старые документы `threads` читаются.
- `adapters/telegram/albums.py` — отправка групп фото/видео, документов и
  аудио через Bot API с сохранением ВСЕХ ID. Смешанные и большие группы
  раскладываются на допустимые серии. Если очередная серия не отправилась,
  уже подтверждённые ID сохраняются как частичная доставка.
- `adapters/telegram/handlers/albums.py` — собирает входящие `media_group_id`
  в коротком буфере (~1 секунда) и отправляет одной логической операцией;
  для private/групп/ответов работает один путь. Буфер ограничен 256
  одновременными альбомами. Существующие входные хендлеры медиасообщений и
  forward стали тонкими адаптерами к RelayService.
- `application/services/admin_details.py` — без изменения поведения вынесены
  методы административного отображения, чтобы сохранить лимит 400 строк.

## Установка

1. Остановить бота (бота не перезапускает патч автоматически).
2. Сохранить backup файлов, `.env` и MongoDB, в первую очередь `threads`.
3. Распаковать весь ZIP в корень проекта с заменой исходников; не удалять `.env`.
4. Установить зависимости, если их ещё нет: `python -m pip install -r requirements.txt`.
5. Выполнить из корня: 
   ```bash
   python -m unittest discover -s tests -v
   python -m compileall -q .
   ```
6. Запустить `python bot.py`. При первом подключении Mongo создаст **два
   новых неуникальных индекса**; существующие записи не преобразуются.
7. Проверить `/health` и `/diag` в Telegram (команды владельца).

## Обязательная живая проверка

Нужны два зарегистрированных неглавных чата A, B и аккаунты для reply.
Заменить ниже `B` на точное имя B, в нужном топике A:

1. **Текст:** `B! проверка` → в B одно сообщение, reply на него → обратно
   в A как ответ на оригинал. Reply из A на сообщение бота → обратно в B.
2. **Фото:** прикрепить фото с подписью `B! фото` → фото приходит B,
   reply на фото возвращается A.
3. **Forward:** в A ответить на чужое текстовое/фото-сообщение текстом `B!`
   → в B появятся заголовок и настоящая пересылка. Сделать reply в B
   **на заголовок** и отдельно **на сам пересланный оригинал**. Оба ответа
   должны вернуться в A и быть привязаны к исходному сообщению.
4. **Sticker / видеокружочек:** в B ответить стикером/видеокружочком
   **на пересланное ботом сообщение**. В A придут заголовок + медиа;
   reply как на заголовок, так и на медиа должен вернуться в B.
5. **Альбом:** из A отправить 3 фото одним альбомом, подпись `B! альбом`.
   В B должны оказаться **все 3**, а не только подписанное фото. Reply
   на последнее фото должен вернуться в A. Аналогично проверить альбом-reply.
6. **ЛС:** `/anon`, затем фото с подписью `B! секрет` и reply на ответ
   бота: в B не должно быть username отправителя. `/deanon` вернёт имя.
7. **Топики:** если A привязан через `/settopic`, команда из чужого топика
   игнорируется, а из привязанного работает. Сменить привязку A, затем
   ответить в B на сообщение, доставленное **до изменения**: ответ должен
   вернуться в исходный топик старой переписки.
8. **Права после redirect:** redirect на главный чат не должен обходить
   запрет для неглавного источника ни для текста, ни для forward/медиа.

## Пример MongoDB-проверки (в консоли mongosh)

В `threads` новая доставка содержит:

```javascript
db.threads.findOne(
  { relay_chat_id: <CHAT_ID_B> },
  { origin_message_ids: 1, relay_message_ids: 1,
    origin_topic_id: 1, relay_topic_id: 1,
    origin_anchor_message_id: 1 }
)
```

Для forward/sticker заголовок + тело: `relay_message_ids` обычно содержит 2 ID;
для альбома из 3 фото — 3 ID; старые поля сохраняются для совместимости.

## Известные ограничения

- Живой Telegram и реальная MongoDB в этой среде **не проверялись**:
  локальные тесты покрывают сервисы и отправщик на SDK-заглушке, но не API.
- Буфер входных альбомов **в памяти процесса**; рестарт в пределах окна
  сбора может потерять ещё не отправленные элементы. Очень поздние части
  группы могут обрабатываться отдельно — это этап для последующих улучшений.
- Нет гарантии exactly-once при неизвестном исходе сетевого запроса Telegram;
  автоматический retry применяется только к однозначной ошибке миграции
  до доставки и к отсутствующему reply anchor при album send.
- Исправление роста массива `stats.timestamps`, глобальных reply lock и
  полноценная мультиплатформенная схема VK/Web — отдельные этапы, не Stage 2.
